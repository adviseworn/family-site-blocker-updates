Family Site Blocker

A browser extension for Chrome, Edge, Brave and Firefox that blocks websites on a list. Its built-in list is exampleadultsite.com (the test case), 20 large adult sites, some newer ones the community list doesn't have yet (AI "companion", image and undress sites, and a few hookup and image sites), and a community list of some 64,000 more (StevenBlack/hosts's adult list, MIT), and you can add your own. From version 1.5.0 it also judges the pictures on every page and hides those that show nudity or, by default, anything suggestive, and from 1.6.0 the videos too, by their frames as they play (see Pictures). Each attempt to open a listed site is noted, with the time: the latest few on its settings page, the whole record on a page of its own (see Blocked attempts).

Test case: navigate to exampleadultsite.com. Expected: the website is blocked. With the extension loaded, you land on a "This site is blocked" page and nothing is fetched from the site. Under the Firefox lock, Firefox blocks it itself before the extension does, so you land on Firefox's own Blocked Page instead.

The project's code is in a repository on GitHub; what the public sees is its site, https://adviseworn.github.io/family-site-blocker-updates/: this guide (the settings page links into it), the update files Firefox reads, and the Firefox lock's profile.

Try it

You need Chrome, Edge, Brave or Firefox on a computer, or Firefox on an Android phone or tablet (see On an Android phone). iPhones, iPads, Safari, Chrome on a phone and browsers built into other apps can't load this extension.

First, get the files onto your computer. On the repository's GitHub page (signed in as one of its members, if the repository is private), click Code, then Download ZIP, and unzip the download. If someone sent you family-site-blocker.zip, unzip that instead.

Chrome, Edge or Brave

  1. Open the extensions page. Click the address bar at the top of the browser window, type chrome://extensions and press Enter (in Edge, edge://extensions). Or open the browser menu (⋮ in Chrome, ⋯ in Edge), choose Extensions, then Manage Extensions if a submenu opens. Type the address rather than clicking it as a link: browsers don't let links open this page.
  2. Turn on the Developer mode switch (top right in Chrome). A Load unpacked button appears.
  3. Click Load unpacked and choose the extension folder inside the unzipped folder. The extension's settings page opens.
  4. In a normal (not Incognito) window, type exampleadultsite.com in the address bar and press Enter. You should see "This site is blocked".
  5. Click Details under Family Site Blocker and turn on Allow in Incognito. Browsers switch extensions off in private windows unless you do this, and the settings page tells you when it is still off.

If chrome://extensions comes up blank, you're probably not in Chrome, Edge or Brave. Firefox has its own steps below.

Firefox

Firefox only keeps add-ons that Mozilla has signed, and from 1.24.0 the signed add-on is published on Mozilla's site, so the short way is to install it from there: in Firefox, open addons.mozilla.org/firefox/addon/family-site-blocker, click Add to Firefox, then Add. Firefox keeps it up to date from there. The unzipped folder itself can be tried straight away, but stays loaded only until Firefox quits; to keep a copy from a file after a restart, it has to be a signed one (see "Keep it installed" below).

Try it (until Firefox quits)

  1. Click the address bar, type about:debugging#/runtime/this-firefox and press Enter. Or open the menu (☰), choose Extensions and Themes, click the gear (⚙) and choose Debug Add-ons.
  2. Click Load Temporary Add-on… and choose the manifest.json file inside the extension folder of the unzipped folder. The extension's settings page opens.
  3. If the settings page's Is it working? board has a line saying Firefox hasn't given the add-on access to websites, click Allow access and confirm. Without that access, pictures aren't judged and safe search isn't turned on; listed sites are blocked all the same (from 1.21.1; until then they opened).
  4. In a normal (not private) window, type exampleadultsite.com in the address bar and press Enter. You should see "This site is blocked". If Firefox is set to never remember history, every window is private, so do step 5 first.
  5. For private windows, type about:addons in the address bar, choose Family Site Blocker and set Run in Private Windows to Allow. Firefox leaves this off for new add-ons, and the settings page tells you when it is still off.

When Firefox quits, it removes the add-on and the sites you added on the settings page.

Keep it installed after Firefox quits

The page on Mozilla's site (see above) is the easy way; what follows is for whoever looks after the add-on, and for installing a signed .xpi from the Releases page by hand (step 7). Signing is free. From 1.24.0 the add-on is listed: published on Mozilla's site under the Mozilla account that signs it, whose display name the page shows as the author. Firefox installs it from there with one click, on a computer or an Android phone, and keeps it up to date from there. Mozilla checks each version and publishes it once its automatic check passes, but holds some for a reviewer, the first public version among them, which can take days. GitHub can do steps 1 to 6 for you, or you can do them by hand.

To let GitHub do it, first save an API key from Mozilla in the repository, once. Signed in at addons.mozilla.org/developers/addon/api/key, generate credentials. Then on GitHub, open Settings → Secrets and variables → Actions and add two repository secrets: AMO_JWT_ISSUER with the "JWT issuer", and AMO_JWT_SECRET with the "JWT secret"; the Mozilla backup and the Firefox lock check use the same key. From then on, when a version lands on main (a change to version in extension/manifest.json), the sign job of Tests and release (.github/workflows/pipeline.yml) runs by itself, after the tests of the same run when the commit still needs them (what a pull request that was up to date with main holds passed them on its branch, and isn't tested twice); or open the Actions tab, choose Tests and release, click Run workflow, choose main and tick sign, to sign by hand. It uploads the add-on to its page with the page's words from scripts/amo-metadata.mjs (the summary, the description, the category, the license, the version's release notes, taken from the title of the commit that made the version, and the notes only Mozilla's reviewers see, which name the unchanged third-party files from extension/vendor/LICENSES.md), waits a little for Mozilla to approve and sign it (5 minutes, and not at all while the add-on has no public version on Mozilla's site; when Mozilla holds a version for a reviewer the job stops there, the version staying at Mozilla, and once Mozilla's email says it's approved, run the workflow by hand as above, which downloads the signed file and carries on; tick publish as well, and the same run publishes the update files), checks that the signed file holds exactly what was uploaded, and publishes a release named after the version (the repository's Releases page) with the signed .xpi, the Mac zip from step 6 and the lock's profile. If Mozilla already has that version, for example because you uploaded it by hand, it downloads the signed file instead. Download them from the release and carry on from step 7.

By hand:

  1. Get the upload file: run npm run package:firefox, which writes dist/family-site-blocker-firefox.zip, or use the family-site-blocker-firefox.zip you were sent. Don't compress the extension folder yourself. Mozilla needs manifest.json at the top of the zip, and Finder's Compress puts it inside a folder. The zip's copy of manifest.json also leaves out the service_worker line, which only Chrome, Edge and Brave use.

  2. Sign in at addons.mozilla.org/developers with the Mozilla account that owns the add-on, open Family Site Blocker under My Add-ons and choose Upload New Version (the first time ever, Submit a New Add-on).

  3. When asked how to distribute it, choose On this site (listed; before 1.24.0 it was On your own, unlisted), then upload the zip. Mozilla runs the same check as the checks job of .github/workflows/pipeline.yml, which finds no errors or warnings in this zip.

  4. When asked whether you need to submit source code, choose No: the add-on's own code isn't minified or compiled, and the TensorFlow.js files under extension/vendor/ are the unchanged builds named in extension/vendor/LICENSES.md, which the notes to reviewers say.

  5. Give the version its release notes and submit it. Mozilla checks it, publishes it on the add-on's page and signs it, at once or after a reviewer has looked at it. When it's approved, download the signed .xpi file from the version's page. Mozilla names it with a code plus the version number, like a138dee9ad3f4f03aa63-1.1.1.xpi, and Finder shows it with a blank document icon.

  6. On a Mac, give it a clear name and the add-on's gate icon. Run npm run package:signed -- followed by the path to the .xpi, for example npm run package:signed -- ~/Downloads/a138dee9ad3f4f03aa63-1.1.1.xpi (dragging the file into Terminal types its path). It checks that the file is Family Site Blocker, signed by Mozilla, and writes dist/family-site-blocker-1.1.1.zip. Double-click that zip in Finder to get family-site-blocker-1.1.1.xpi with the gate icon. It's the same signed file, so it installs the same way. To give it to another Mac, send the zip: the .xpi on its own arrives without the icon.

    Without Node, you can do this by hand. Rename the file, then open extension/icons/icon128.png in Preview and choose Edit → Select All, then Edit → Copy. Select the .xpi, choose File → Get Info, click the small icon at the top of the window and choose Edit → Paste. Neither the name nor the icon affects Mozilla's signature, and Firefox shows the add-on as Family Site Blocker either way.

  7. In Firefox, remove the temporary copy if it's still loaded (on about:debugging#/runtime/this-firefox). Then open about:addons, click the gear (⚙), choose Install Add-on From File…, pick the .xpi and click Add. Tick Allow this extension to run in Private Windows if Firefox offers it.

    Double-clicking the .xpi in Finder won't work at first: macOS doesn't link .xpi files to Firefox, so it says no application is set to open it. To change that, select the file, choose File → Get Info, set Open with to Firefox and click Change All…. If Firefox isn't listed, choose Other…, set Enable to All Applications and pick Firefox. From then on, double-clicking a .xpi opens Firefox, which asks whether to add it.

  8. Quit Firefox, open it again and visit exampleadultsite.com. It's still blocked, and sites you add on the settings page now stay too.

For a later version, raise version in extension/manifest.json: once that is on main and its tests pass, the sign job runs by itself (or run the workflow by hand, as above); or run npm run package:firefox, upload the new zip on the same add-on's page and carry on from step 5.

Version 1.3.0 asks for two permissions earlier versions didn't have, to note blocked attempts, 1.3.4 for a third, to add earlier visits from the browser's history, and 1.3.6 for a fourth, to remove bookmarks to listed sites (see Blocked attempts). Installing it by hand over an older version, Firefox asks you to accept them; under the lock, Firefox grants them itself. Version 1.11.0 asks for a fifth, alarms, to keep track of when it is running (see Was it ever off?); neither Firefox nor Chrome shows a prompt for that one, so the update installs by itself. In Chrome, Edge and Brave, click the reload button under Family Site Blocker on the extensions page after replacing the folder's files, and if the extension shows as switched off with a note about new permissions, accept them there.

Let it update itself (Firefox)

From 1.24.0, Firefox keeps the add-on up to date from Mozilla's site, as it does for every add-on installed from there: it asks about once a day (and when someone chooses Check for Updates from the gear menu in the Add-ons Manager) and installs the newest version Mozilla has approved, on a computer or a phone, so the add-on no longer names an update address of its own. Versions 1.3.2 to 1.23.0 keep themselves up to date another way, which the Firefox lock installs from: an update manifest, updates.json, which lists the signed versions and where to download them; Firefox reads it about once a day, and installs the newest version listed, after checking the file against the hash in the manifest. Firefox only fetches these without signing in, so they live on the project's public site, the GitHub Pages site of a repository of its own: adviseworn/family-site-blocker-updates, at https://adviseworn.github.io/family-site-blocker-updates/. Beside this guide (its front page, with the add-on's icon) and the lock's profile, the site holds the update manifest and the signed .xpi files of the newest versions (anyone can download those, the same files family members install), and nothing else; the source stays in the code's repository. The newest version is there a second time as family-site-blocker.xpi, one name that never changes, which the Firefox lock installs from. The update-files job of Tests and release publishes them after each release: it fetches the newest signed versions from the releases, where the sign job puts each version's files (scripts/release-files.mjs), builds the update files (scripts/updates-manifest.mjs) and the guide (scripts/guide.mjs) and pushes them to that repository's gh-pages branch, which GitHub Pages serves, showing a change a minute or two later. To publish them again by hand, open the Actions tab, choose Tests and release, click Run workflow, choose main and tick publish. The site is at the address the copies from 1.3.2 to 1.23.0 name, so those update themselves from it. From 1.25.0 to 1.29.0 the project was on GitLab, with its site at https://adviseworn.gitlab.io/family-site-blocker/: those versions' settings pages link there, and a lock made from one of them installs 1.29.0 from there, which Firefox then updates from Mozilla's site. That site stays as it was and gets nothing newer; installing the current profile once moves a lock to the address above.

The job pushes to the site's repository with a deploy key. To set that up, once:

  1. Make a key for it. In Terminal: ssh-keygen -t ed25519 -N "" -C "family-site-blocker updates" -f ~/Desktop/updates-key. That writes two files on the Desktop.
  2. In the site's repository, open Settings → Deploy keys → Add deploy key, paste the contents of updates-key.pub, tick Allow write access and add it.
  3. In the code's repository, open Settings → Secrets and variables → Actions and add a secret named UPDATES_DEPLOY_KEY with the contents of updates-key (the one without .pub, all of it). Then delete both files from the Desktop.
  4. Publish by hand, as above, to see it work.

If the site's repository ever has to be made again: a public repository named family-site-blocker-updates under the same account, empty; the first push of a gh-pages branch (step 4) switches GitHub Pages on for it.

The update address only works from a version that carries it (1.3.2 to 1.23.0; from 1.24.0 Firefox asks Mozilla's site instead): such a copy updates itself to the newest version on the site, and from then on from Mozilla's site. Only an account whose copy is older than 1.3.2 needs a later version put in once. On a Mac with the lock, the lock does that: it installs the newest signed version from the update site, and installing a new copy of the profile makes Firefox do so again in every account at its next start (see the next section). Without the lock, install it by hand once (step 7 above), the last time. Firefox installs an update silently when it asks for no new permissions; a version that adds one waits in each account until someone accepts it (Firefox shows it under the gear menu and in the Add-ons Manager), unless the lock installs it, in which case Firefox grants them itself. The lock's settings also keep Update Add-ons Automatically switched on (ExtensionUpdate).

On an Android phone (Firefox)

Firefox for Android, the ordinary one from Google Play, installs the add-on from Mozilla's site with one tap (from 1.24.0, when the add-on was published there); Chrome and the other Android browsers can't run extensions, so a phone is covered only inside Firefox.

  1. Install Firefox from Google Play (not Nightly or Beta) and open it once.
  2. In Firefox, open addons.mozilla.org/firefox/addon/family-site-blocker and tap Add to Firefox. When Firefox lists what the add-on asks for, tap Add. Tick Allow in private browsing if Firefox offers it; otherwise the switch is under ⋮ → Extensions → Family Site Blocker.
  3. Type exampleadultsite.com in the address bar. You should see "This site is blocked".
  4. The settings page is under ⋮ → Extensions → Family Site Blocker → Settings. If its Is it working? board says Firefox hasn't given the add-on access to websites, tap Allow access there: listed sites are blocked without it (from 1.21.1; until then they opened on a phone that left it off), but pictures aren't judged and safe search isn't turned on until it is given.

Before 1.24.0 the add-on wasn't on Mozilla's site, and a phone could only install the signed .xpi from the Releases page through Firefox's hidden debug menu, the route Mozilla documents on Extension Workshop under "Installing self-distributed extensions": tap ⋮ → Settings → About Firefox, then the Firefox logo five times quickly, until a note says "Debug menu enabled"; back under Settings, Advanced then shows Install extension from file, which takes the downloaded .xpi. That route still works, for a version Mozilla hasn't approved yet, say; the menu switches itself off when Firefox restarts, the add-on doesn't.

A phone differs from a computer in three ways:

  • There is no lock. The Firefox lock is a Mac profile, so on a phone anyone who can open Firefox's settings can switch the add-on off or remove it; the Is it working? board's lock line says so, as "No Firefox lock on a phone". Family Link and the phone's own controls can keep other browsers off the phone, but can't lock an add-on.
  • Firefox for Android doesn't open its history or bookmarks to add-ons. The record notes tries as they happen, but the look through the browser's history, the sweep of the address bar's history and the record's "off" bands don't work there, and the record page says it couldn't look through the browser's history, which is expected on a phone.
  • Newer versions arrive from Mozilla's site by themselves, as for any add-on installed from there. A copy from before 1.24.0, installed from a file, reads the update manifest instead (see Let it update itself), which brings it to 1.24.0; from then on it too updates from Mozilla's site.

Lock it, so nobody can switch it off (Firefox on a Mac)

On its own, the add-on can be switched off or removed in the Add-ons Manager by anyone using Firefox. The Firefox lock stops that. Firefox installs the add-on itself and gives no way to switch it off, remove it or take away its access to websites. The lock also turns off private windows (add-ons don't run there unless someone allows it), Firefox's own menu items for Troubleshoot Mode, about:config and Refresh Firefox, and, from version 1.10.3, the developer tools (the Inspector and the rest of the toolbox, which could otherwise reveal a hidden picture or the page behind the filter), which could get round it, and keeps automatic add-on updates switched on. It applies to every account on the Mac, yours included.

On a Mac, Troubleshoot Mode can still be started from outside Firefox, and no add-on runs there. So the lock also gives Firefox its own copy of the built-in list, which Firefox enforces itself: those sites stay blocked in Troubleshoot Mode, and while the add-on is switched off. Firefox takes at most 1,000 entries for it, so the copy holds the whole adult top-level domains .xxx, .porn, .sex, .adult and .sexy as one entry each (every site on them, listed or not), the test case and the large sites of starter.txt, and then the built-in sites people visit most, in that order, until it is full (see Adding sites). Firefox blocks them before the add-on gets to them, so for them you see Firefox's Blocked Page rather than the add-on's. The other sixty thousand or so built-in sites, and sites added on the settings page, still get the add-on's page, and aren't blocked in Troubleshoot Mode (see What can still get round it below).

The lock works alongside another blocker that sets Firefox's settings too, such as Plucky. Both blockers' settings stay in force (Limits below has the exceptions).

You need an administrator account, and the Mac has to be online when Firefox first starts in an account, because the lock makes Firefox install the newest signed version from the update site (https://adviseworn.github.io/family-site-blocker-updates/family-site-blocker.xpi, see Let it update itself). The lock only stops people who don't know an administrator's password: anyone who types one can remove it, even from a Standard account, and then switch the add-on off. A profile installed by hand can't prevent that, because macOS lets an administrator remove it even when it has a removal password of its own. So the person it's for needs a Standard account (System Settings → Users & Groups) and mustn't know the password of any administrator account on the Mac.

  1. Double-click mac/family-site-blocker-firefox.mobileconfig, from the unzipped folder, the release page or the site (https://adviseworn.github.io/family-site-blocker-updates/family-site-blocker-firefox.mobileconfig). From 1.23.0 the add-on's settings page has the same file: on a Mac, whenever its lock line asks for the profile to be installed, a Save the lock's profile button saves it to the downloads, so a Mac whose Firefox can't reach GitHub, or that sits on an older copy, has it at hand. macOS says the profile was downloaded. That doesn't install it yet.
  2. Open System Settings → General → Device Management. If Family Site Blocker for Firefox is already listed as installed from an earlier copy, select it, click the minus button (−) and enter your password, so the new copy replaces it. Then double-click the downloaded Family Site Blocker for Firefox and click Install…. macOS asks for the name and password of an administrator account. If your own account is one (Users & Groups shows "Admin" under your name), that's your login password. Otherwise, someone with an administrator account can type theirs here.
  3. Quit Firefox (Firefox → Quit Firefox, or ⌘Q; closing its windows isn't enough) and open it again. Firefox only reads the lock when it starts, so until then the add-on can still be switched off. To check that the lock is on, type about:policies in the address bar. The Active tab lists Extensions, with family-site-blocker@parental-controls.local under Locked, DisablePrivateBrowsing, Preferences (with devtools.policy.disabled and extensions.dnr.enabled locked on), and WebsiteFilter, with the built-in sites under Block. Settings from other programs are listed there too: Plucky's include ExtensionSettings, with its own add-ons. The add-on's settings page says so as well: the lock line of its Is it working? board reads "The Firefox lock is in force", and from version 1.8.0 says which copy of the profile is installed, "this version's copy (1.8.0), with 1,000 entries in Firefox's own list" (see Settings page). Visiting exampleadultsite.com now shows Firefox's Blocked Page.
  4. Open the Add-ons Manager. Family Site Blocker has no on/off switch any more, and its ⋯ menu says Can't Be Removed. If it had been switched off before, Firefox normally switches it back on when the lock installs it. If it's still off (for example because a different version had been installed by hand), it shows a switch to turn it on. Turn it on once, and the switch disappears for good.

From 1.22.0 the add-on's record notes when the lock was in force and when not, as a row on Every try at each Firefox start that found it changed (see Was it ever off?). Firefox installs the add-on from that address once in each Firefox profile for each copy of the lock, and tries again at the next start if it couldn't fetch it. It doesn't look there again by itself; from version 1.3.2 the add-on updates itself instead (see Let it update itself), and the lock lets it. When the lock changes, for example because the built-in list changed (see Adding sites), npm run build writes a new copy of the profile, and installing it as in steps 1 and 2 gives Firefox the new settings, and makes it install the newest version again in every account at its next start, so an account still on an older copy catches up without anyone at the screen. Each copy says which it is: the profile's description in Device Management names the version it was built with ("the copy from version 1.8.0"), and the profile hands the add-on the same stamp through Firefox's 3rdparty policy (its managed storage, which nothing but a policy can write), so the settings page's lock line says whether the copy installed carries this version's list and settings. From 1.15.0 the stamp also carries a digest of Firefox's own list and the lock's other settings, and the line compares by it: a copy from an older version is fine while nothing in it has changed ("the copy from version 1.11.3, with the same list and settings as this version's"), and only a copy whose list or settings differ is marked as something to do ("Install the current profile so Firefox's own list and the lock's other settings catch up"); before 1.15.0, every release's copy counted as older (#78). A copy from before 1.15.0 carries no digest, so the line goes by its version: while the add-on's own list and settings are still the ones the profiles of releases 1.10.5 to 1.14.0 carried, its own copy of the stamp says so (sameSince in extension/rules/lock.json, 1.10.5, which the build works out from the digest alone, so a build on any branch writes the same), and a later list or setting is in no profile from before the digest, so such a profile is an older copy. A copy from before 1.8.0 carries no stamp, and the line says so. To take the lock off, select the profile in Device Management, click the minus button (−) and enter an administrator's name and password. Family Site Blocker stays installed and keeps blocking, but it's an ordinary add-on again, so anyone can switch it off.

Close the Option key, too (optional)

Holding the Option key (⌥) while Firefox opens offers Troubleshoot Mode, where no add-on runs, and Firefox checks that key before it reads the lock. It skips the check when the environment variable MOZ_DISABLE_SAFE_MODE_KEY is set, and mac/local.parental-controls.family-site-blocker.firefox-troubleshoot-key.plist is a launch agent that sets it in every account at login, for the apps opened from the Dock, Finder and Spotlight. Neither the add-on nor the profile can put it in place (an add-on can't touch /Library, and a profile installed by hand carries settings, not files), so scripts/mac-installer.mjs builds an installer package for it: npm run mac-installer, on a Mac (it needs Apple's pkgbuild), writes dist/mac/family-site-blocker-firefox-troubleshoot-key-<version>.pkg. On GitHub, Mac files for a release (.github/workflows/mac-installer.yml, started by hand from the Actions tab) builds it on a GitHub-hosted Mac and adds it to a version's release, under Assets. The releases up to 1.23.0 carry it; 1.29.0, released while the project was on GitLab, which has no Macs, doesn't:

  1. Double-click the .pkg. The package isn't signed with Apple (that needs a paid developer account), so macOS says it can't check it for malicious software. Open System Settings → Privacy & Security, scroll down, click Open Anyway next to its name, and confirm; then double-click it again if it didn't open by itself.
  2. Installer shows what it does; click through and give an administrator's name and password, as for the profile. It puts the agent in /Library/LaunchAgents, owned by the system, and closes the key at once in every account logged in; the other accounts get it at their next login.

Or by hand, with the file from the unzipped folder, in Terminal (it takes effect in each account at its next login, so log out and in once):

sudo cp mac/local.parental-controls.family-site-blocker.firefox-troubleshoot-key.plist /Library/LaunchAgents/
sudo chown root:wheel /Library/LaunchAgents/local.parental-controls.family-site-blocker.firefox-troubleshoot-key.plist

To check, run launchctl getenv MOZ_DISABLE_SAFE_MODE_KEY in Terminal: it prints 1. From then on, holding Option while Firefox opens just opens Firefox. Troubleshoot Mode can still be started from Terminal (open -a Firefox --args --safe-mode), which Screen Time (Content & Privacy → App Restrictions) can keep out like any other app, and macOS lists the agent under System Settings → General → Login Items & Extensions, where an account may be able to switch it off (after which its next login has the key back): it is a hurdle, not a lock. To remove it, delete the file from /Library/LaunchAgents with sudo rm and log out and in; the package leaves nothing else behind.

Make the lock hold against the administrator password, too

Nothing installed on a Mac can hold against someone who types an administrator's password: macOS lets them remove any profile, this lock included, and change anything else. (A Mac that a company enrolls through Apple Business Manager and manages with an MDM service can get a profile that even an administrator can't remove, but that needs an organisation with a D-U-N-S number, an MDM service and erasing the Mac.) So the way to make the lock hold is to make sure nobody, you included, knows the administrator password at a moment's notice. The locked-away password, on a page of its own reached from the settings page, is for that: the password gets a random value that only comes back after a wait of up to 2 days.

Work through the steps in this order. Until step 6 is checked, the new password has a copy you can still get at, so a slip can't lock you out.

  1. Turn on FileVault while your everyday account is still an administrator: System Settings → Privacy & Security → FileVault. Without it, someone can reset the administrator password from macOS Recovery. Anyone who has its recovery key can do that too, so the key gets locked away with the password in step 5.
    • On macOS 15 Sequoia or earlier, if FileVault is off, turn it on and choose Create a recovery key and do not use my iCloud account. The key is shown only once, so write it on paper for now.
    • On macOS 26 Tahoe or later, FileVault may already be on. What can still get round it

On a Mac, holding the Option key (⌥) while Firefox opens, or opening it with --safe-mode, still offers Troubleshoot Mode, where no add-ons run, this one included; Firefox can stop that only on Windows, and the launch agent above closes the Option key but not the Terminal. Firefox's own copy of the list still blocks there: every site on .xxx, .porn, .sex, .adult and .sexy, the large sites, and the built-in sites people visit most, 1,000 entries in all. The other built-in sites open, and so do sites added on the settings page, explicit search results and pictures (safe search and the picture filter need the add-on), and images and scripts that an allowed page loads from a blocked site. What it blocks

  • The listed domain and every subdomain (www., m., cdn.…), on any scheme and port, however the address is written (upper case, trailing dot, user:pw@, full-width letters).
  • The same site reached indirectly: a link, a popup, a redirect, a form post, a frame inside another page.
  • Anything an allowed page tries to load from the site: images, scripts, styles, frames, fetch, XHR, WebSockets. These fail silently.
  • Lookalikes are left alone: notexampleadultsite.com, exampleadultsite.com.example.org, exampleadultsite.co.

It blocks by domain. It can't block one page of a site, and it doesn't read page content, so an adult site that isn't on the list isn't blocked.

Safe search

A list can't filter search results, and Google Images, Bing and the rest show explicit results with their own filter off. From version 1.4.0 the extension keeps those filters on: a search on Google, Bing, DuckDuckGo, Yahoo or Brave Search goes out with the engine's strict setting added to its address (safe=active, adlt=strict, kp=1, vm=r, safesearch=strict), whatever the engine's own settings say and whichever way the search was typed. (Until 1.25.0 every request to YouTube also carried the header that keeps it in Restricted Mode; that hid ordinary videos too, a finance podcast among them, and Restricted Mode allows no exceptions, so from 1.26.0 YouTube is left alone.) The browser does this itself from rules the extension gives it (extension/rules/safe-search.json, written by npm run build from extension/lib/safesearch.js), before the request goes out, so there is no moment when the unfiltered page loads; a search whose address already has the setting is left as it is, and so are the engines' other pages. The settings page's Safe search section has a Google search to try: the address gains safe=active. Other search engines, and sites with a search of their own, aren't covered, and the filters are the engines' own, with their misses. Under the Firefox lock this needs the add-on running, so it doesn't apply in Troubleshoot Mode.

Pictures

A list of sites can't touch one picture on an ordinary site: a magazine article that opens with a stock photo of a woman in lingerie, say. From version 1.5.0 the extension also judges pictures themselves. Every <img> a page shows is kept hidden until the background script has judged it, then shown or kept hidden; icons and other small pictures (under about 64 pixels square) are shown at once, and a long page costs only what comes near the view. The judge is NSFWJS's MobileNetV2 model (MIT) on TensorFlow.js (Apache 2.0), both bundled in extension/vendor/ and extension/models/, run through WebAssembly on this computer: no picture and no score leaves it. It gives five scores that add up to one: drawing, hentai, neutral, porn and sexy, "sexy" being its word for suggestive but not explicit, such as lingerie, swimwear or a pose. From 1.20.0 there are two judges: that model is quick, tens of milliseconds a picture, so every picture goes through it, but it hides one ordinary photo in fourteen by mistake, so a picture it would hide is judged again by NSFWJS's InceptionV3 model, ten times the size and ten times slower, and that second opinion decides. On 1,300 ordinary photos (300 everyday ones, many with people, and the 1,000 ImageNet sample pictures) the pair hid 31 by mistake at full size where the first judge alone hid 92, and 2 in 300 at thumbnail size where it hid 13, while all ten swimwear and lingerie pictures among them stayed hidden; NSFWJS's mid-size model, tried as well, hid fewer by mistake but let eight of those ten through, and so was passed over. The second model loads when first needed, in a few seconds, takes 22 MB of the add-on and about 120 MB of memory while it is loaded, and the record notes the deciding scores; the settings page says how many pictures were judged twice.

The Pictures section of the settings page chooses what is hidden: Nudity and anything suggestive (the default: hidden when porn, hentai and sexy together reach 0.4) or Nudity only (porn and hentai together reach 0.4). There is no off. The page's Is it working? board says how many pictures and video frames were judged and hidden since the browser started, and how the judging runs. Hidden pictures go into the record: a page of its own, Pictures hidden (linked from the record page), sums them up by site, and from 1.16.0 each one is a row on Every try (see Blocked attempts), among the tries at listed sites, marked Picture hidden or Video hidden, with why, the score that decided (from 1.21.0; both scores until then) and the picture's address, which copies when clicked (from 1.21.0; a Copy address button until then, and until 1.16.0 the Pictures hidden page listed them itself); See them among every try on that page shows those rows alone, and a site in its by-site table shows that site's. A picture hidden on a score under 0.6 is marked borderline, and the summary counts those: that is where a harmless picture hidden by mistake will be. To look at one, from 1.17.0, Look at it on its row: the page asks why, there in the row under the button so that the page stays where it was (once, for as long as it stays open, as the locked-away password's page asks before unlocking), notes the look on the row with the time and the reason, and shows the picture there: the filter runs in web pages, not in the add-on's own, so a picture shown there isn't hidden again. From 1.17.4 it is shown from a smaller copy kept apart from the record when the picture was hidden (the latest 100, at most 512 pixels on the longer side and about 4 MB in all, the oldest going first), so a look doesn't depend on the picture's address, which may be the picture itself written out (a data: address, of which the record keeps only the start), may have lost the picture, or may not answer; a picture hidden before 1.17.4, or among the oldest, is fetched again from its address by the background script, the way it was fetched to be judged, and the row says so, or says what stood in the way. Two marks follow, Hidden by mistake and Rightly hidden, kept on the row and counted in the summary with the looks, so the filter's mistakes can be told from its catches; from 1.18.0 a mark goes to every row that shows the same picture (hidden again at the same address, or the same picture at another, which the kept copies tell), and the hidden pictures can be checked in bulk: Check them in bulk, under the pictures' note on Every try (and a link on the Pictures hidden page), opens a page of its own, Check the hidden pictures, that shows every hidden picture with a copy kept together, one tile each however many rows it has, after asking why once (every picture shown there is a look, on the record with the reason), with the two marks on each tile and keys for them (the arrows move from picture to picture, M marks one hidden by mistake, R rightly hidden, and a mark moves on to the next not yet marked), a box to show the marked ones too, and one button that marks all that are left as rightly hidden. There is no password (#58 proposed one): anyone who can open the page can look, and every look is on the record, as every try at a listed site is. On an account kept to Firefox that is the one way to see a hidden picture, and it leaves a trace; on an account with another browser, the address on the row, which copies when clicked, did that already, without one. A video shows as itself or as its poster when the record holds that address; a page's address, which a video the page made itself is noted under, gives a link to the page, where the video is judged again. A picture with no copy kept and gone from its address can't be shown. From 1.19.0 a mark does something: Hidden by mistake shows the picture again from then on, on the pages open (each page's content script judges again what it hid there, and the judge lets that picture through) and wherever it appears later, known by its address or by its kept copy (the copy's hash and length, as duplicates are told), so the same picture at another address, or written out as a data: address, is known too; Rightly hidden hides it again from the next page load. The pictures shown again are a list of their own (picturesShown, up to 1,000, the oldest going first), kept apart from the record, so a picture stays shown when its row has gone; a video's mark stays a note, a video being judged by its frames under an address that may be its poster's or its page's. There is no password here either: a mark is on the record with the look before it. From 1.18.3 a picture is read from its address only up to 20 MB, and a video up to 50 MB, whether to judge it, to copy it or to show it again, so that a huge file can't fill the add-on's memory, which in Firefox every one of its pages shares with the background script: a bigger picture is shown on its page without being judged, as one that can't be fetched is, and on Every try the row says how big is too big. Nothing on the page un-hides a picture; if a harmless picture was hidden, the Nudity only setting hides fewer. A hidden picture keeps its place on the page, blank; a page's script can't bring one back by taking the mark off, because the picture is judged again at once. From 1.26.1 a captcha's pictures are left alone: the frames that Arkose Labs, hCaptcha, reCAPTCHA and Cloudflare's challenge put on a page (GitLab's and GitHub's sign-in among many) aren't judged, because their pictures are the puzzle, and with one of them blanked the puzzle can't be solved, which kept a sign-in from finishing. From 1.27.0 a picture kept hidden for 20 seconds without a verdict is noted in the record: a Picture unjudged row on Every try (and in the saved file) with the picture's address and what the judge was doing at the time (fetching the picture, judging it, asking the second judge, or nothing, the request never having reached it), which becomes Picture judged after 47 s: shown (or hidden) when the verdict comes after all. The picture stays hidden until it does, as before: showing it unjudged after a wait would change what the filter lets through, which is a separate choice.

The judge is a machine's, and it errs both ways: it misses some pictures, and hides the odd harmless one (swimwear, art, a medical page), more so under the default setting. A picture the page made itself (a blob: address) or one the background script can't fetch is shown as it is, and pictures inside shadow roots aren't judged.

Backgrounds. Not every picture is an <img>. X shows a tweet's picture as the background of a div, set in the element's own style (background-image: url(https://pbs.twimg.com/media/…)), with a see-through <img> of the same address over it for the alt text and for saving; the filter judged and hid that <img>, which nobody could see anyway, and the background stayed in view (#80). From version 1.10.1 a picture an element's own style sets as its background is judged like an <img>: the element has no background until the picture has been judged (its size, and whatever is in it, stay as they are), every address in its background-image is judged (a gradient or image-set() with several pictures among them), and the element keeps no background if any of them is one to hide. Small means what it means for an <img>: an element under 64 pixels square showing pictures that are all under that (an icon, a sprite) is shown without being judged; a small thumbnail of a big picture is judged. A new address in the style, or the page taking the mark off, means judging again. Hidden backgrounds go into the record like pictures, by their address, so a tweet's picture appears there once, under x.com. Backgrounds set in stylesheets (a class, not the element's own style), and one that reaches the element through a CSS custom property, aren't seen. Under the Firefox lock the judging needs the add-on running, so it doesn't happen in Troubleshoot Mode. Judging takes about a tenth of a second a picture through WebAssembly; the first picture after the browser starts waits a moment longer while the model loads.

Video. A site that isn't on the list can show a video that a list can't touch either: a TikTok video of a woman in lingerie was the case that showed it (TikTok, like Instagram or X, is deliberately kept off the list). From version 1.6.0 every <video> is judged the same way as a picture, and by the same judge. A video stays hidden until its poster, if it has one, and its first frame have been judged; then, while it plays, one frame every second and a half is judged, and one after each seek. From 1.11.1 the first frame is read once the browser has put it up, not as soon as its data has arrived: until then a browser can hand over a black frame, which would pass for a photo and show the video until its next frame was judged, a second and a half later. A frame is copied small (224 pixels square, as the judge scales it anyway) by the page's content script and judged by the background script like a picture; a video whose frame or poster is judged the way a hidden picture would be is hidden and paused, and stays so for as long as it keeps that source, whatever the page does to its mark; a new source is judged afresh. Hidden videos join the record like pictures, as Video hidden rows, under the video's own address, its poster's or, for a video the page made itself (a blob: address, as players that stream do), the page's. A hidden video keeps its place on the page, blank, so pages built around one still work; the sound stops with it. What it can't judge: in Chrome, Edge and Brave, a video whose frames the page itself may not read, that is, one served from another site without that site's permission, is judged by its poster alone, or shown as it is when it has none (Firefox lets an add-on read every video's frames, so there it is judged too); videos that stream (YouTube, TikTok, most players) hand the page their frames, so those are judged everywhere. Protected video (films from a subscription service) gives no frames to read and is shown. A video that turns from harmless to not is hidden within a second or two, so a moment of it may be seen. A video inside a shadow root isn't judged, as a picture there isn't.

The device's own camera. A page can show a video that is no file at all: the stream the browser hands it when you allow it to use the camera (getUserMedia), as the New Zealand travel-authority site does for a passport photo. Judged by its frames like any video, with the person close to the lens and filling the picture, the camera's video was hidden and paused a moment after it appeared, and noted under the page's address, since a stream has none of its own (#84). From version 1.10.2 a video of the device's own camera is shown as it is and never judged: it shows what is in front of the computer, which the filter can't hide from the person sitting there, and hiding it broke the pages that use a camera (passport and ID photos, a video call's own picture, scanning a code). The content script tells the camera by the stream's tracks: every one of them must come from a camera the browser lists for the page, which is what a getUserMedia track's deviceId promises. Any other stream is judged by its frames as before: the other people in a video call, whose pictures arrive through a peer connection, and a stream the page made from its own drawing (a canvas); a hidden one is noted under the page's address, as a blob: video the page made is.

Developer tools. The filter runs in the page, and the browser's own developer tools are above it. Open the Inspector on a hidden picture, and hovering its address shows a preview of it; the Network panel shows the bytes of anything the page loaded, blocked pictures among them; the Console reaches them too, and can take the mark off every hidden picture at once (it is put back at once, but a script that reads the addresses first has them). The add-on can't police any of this, because the tools aren't part of the page. On a Mac the Firefox lock closes them (from version 1.10.3): it locks the devtools.policy.disabled preference, which Firefox checks before it opens a toolbox, so the Inspector, the Console and the Network panel don't open from F12, the right-click Inspect or the menu, as the lock closes the other ways round at the keyboard (#86). It locks that one preference rather than Firefox's broader DisableDeveloperTools policy, which would also switch off remote automation (Marionette), the lock's own tests among its users. In Chrome, Edge and Brave an administrator can turn the tools off with the DeveloperToolsAvailability policy (see Limits). Without a lock, anyone who can open the developer tools can see a blocked picture through them, as anyone who can open the extensions page can switch the add-on off.

The Real pictures check (npm run check:pictures, or the workflow of that name, started by hand from the Actions tab) judges the real pictures listed in test/real-pictures.txt through the extension in Chromium and prints their scores against what the list expects: the lingerie photo from the article above comes out sexy 0.97, hidden under the default setting and shown under Nudity only; the ordinary photos listed with it come out neutral. When a picture is judged wrongly in use, add a line for it there, so the thresholds in extension/lib/pictures.js can be checked against it.

Adding sites

  • Your blocked sites on the settings page: one site per line, saved straight away. Pasted addresses are cleaned up (https://www.Example.com/a?b becomes example.com) and hosts-file lines (0.0.0.0 example.com) work too. From 1.17.1 a tab already showing a site you add is sent to the block page when you save, as a page it loads from then on is; before, such a page stayed as it was until it was loaded again. The block page takes the page's place in the tab's history, so Back doesn't bring it back. The same happens to a tab showing a site the built-in list gains when a version is installed. A listed site inside another page (a frame) is left as it is, though nothing more can load into it.
  • The built-in list lives in blocklists/*.txt: starter.txt, the test case and the large sites, which Firefox's own copy (the lock) takes first; community.txt, the "porn" extension of StevenBlack/hosts on its own, some 64,000 sites gathered from lists its maintainers rebuild every few days (MIT; it holds Clefspeare13/pornhosts and bigdargon/hostsVN's adult list, MIT too); and popular.txt, the built-in sites people visit most, in order (below). npm run blocklist fetches the latest copies of both; any other .txt file saved there is taken too. After a change, run npm run build, which rewrites the rules (extension/rules/, split into files Mozilla's linter will read) and the lock's profile, then release a new version. Large lists are fine: 400,000 domains in the built-in list and 300,000 pasted into the settings page both worked in testing.
  • Sites to leave out go in blocklists/never.txt, with a reason each. The settings page can't remove built-in sites, and the community list carries the odd ordinary site (a lifestyle magazine, a film database, a search engine), and one entry, www.b-cdn.net, that with its www. dropped would block Bunny CDN, a network ordinary sites load pictures and scripts from. The build leaves the sites named there out of the rules, domains.json and the lock's copy; a line takes out that one domain, so a host listed under it on its own stays blocked. The fast checks make sure those sites and a list of well-known ones never get onto the built-in list (test/blocker.test.mjs, NEVER_LISTED), and npm run blocklist prints the most visited sites on the list whose names don't look adult, as candidates.
  • npm run build also writes the Firefox lock's profile, mac/family-site-blocker-firefox.mobileconfig, with Firefox's own copy of the list, which Firefox enforces itself. Firefox takes at most 1,000 entries there, and they are match patterns, so one entry can take a whole top-level domain: the copy starts with .xxx, .porn, .sex, .adult and .sexy as one entry each (scripts/firefox-lock.mjs, WHOLE_DOMAINS; the first four are ICM Registry's adult-only domains, .sexy is adult in practice), which cover some 1,300 of the list's sites and every site on those domains that no list has yet, then the sites of starter.txt, then popular.txt in its order, then the other files by name, until the 1,000 are full. The build says how many sites were left out; the add-on still blocks those while it runs. On a Mac with the lock, install the new profile (steps 1 and 2 of the lock) to bring Firefox's copy up to date; until then the settings page's lock line says an older copy is installed, and from 1.23.0 offers to save the new one. The build also stamps the profile with the version it was built with, the size of Firefox's copy and (from 1.15.0) a digest of the copy and the lock's other settings, and writes the same stamp to extension/rules/lock.json, which is how the page tells, and why a profile from an older version isn't called old while nothing in it has changed.
  • popular.txt is written by npm run blocklist from the Chrome UX Report's top million sites, Google's count of real page loads in Chrome, which zakird/crux-top-lists caches as a CSV (Google's public dataset, CC BY-SA 4.0 as Tranco gives it; the file takes the order of some two thousand sites from a million, not the data). It ranks sites in bands (the top 1,000, 5,000, 10,000, 50,000 and so on) and gives no order within a band, so there the Majestic Million decides (CC BY 3.0; a ranking by links from across the web, which npm run blocklist also fetches), sites it doesn't rank last and alphabetical among themselves. The file lists the built-in sites best band first, with the band and the Majestic place in a comment; every site in it is on starter.txt or community.txt already. The order matters at the edge: the copy's last band has room for about a third of its sites, and which third used to be the alphabet's choice. Before it, the lock's copy was starter.txt and then the community file in file order, which put 938 small Vietnamese sites in Firefox's copy and 18 of the 634 listed sites in the top 10,000 of the web; now the copy holds every one of them (632, two having come off the list in never.txt) and 973 of the 1,734 in the top 50,000.

Blocked attempts

Each time a page on a listed site is opened in a tab, by typing the address, following a link, a redirect or a form post, the extension notes the time and the site. A site is noted under its listed name (exampleadultsite.com for www.exampleadultsite.com/page), whether the block page stopped it or, on a Mac with the Firefox lock, Firefox's own Blocked Page did. Tries at the same site less than two seconds apart count as one, so a reload isn't a new try. A visit found in the browser's history (below) isn't such a repeat: from 1.11.2 a try within two seconds of one is noted all the same, where before it was lost when a site that had just been visited was added to your list and tried again at once.

The settings page shows the summary and the latest three under The record, newest first, with two buttons under them, each opening a page of its own in a tab of its own. See every try (from 1.15.1 straight from the settings page; before, by way of the record page) leads to every try, grouped by day, newest first, with the times the extension was off laid in among them (see Was it ever off?), the pictures and videos hidden (see Pictures), the locked-away password's record (see Locked-away password), from 1.22.0 the Firefox lock's (see Was it ever off?) and, from 1.27.0, the pictures that waited long for a verdict (see Pictures); the link shows whenever that page has something to show, a try, a time off, a picture hidden or one that waited, or an entry of the password's record or the lock's, and counts the tries. See the record by site opens the record page: the record summed up by site (how many tries, the first and the latest, how many got through), most tried first, since when the extension has been watching and whether it was ever off, the line that says when the browser's history was last looked through (below), with a line each for the two other parts of the record, the pictures hidden and the sites that might belong on the list, which have pages of their own (see below); See every try there leads to the same page, and choosing a site in the by-site table leads to it showing that site alone, its tries and the pictures hidden there. Save as a file, on both pages, saves the whole record as a CSV file (family-site-blocker-record-<date>.csv in the browser's downloads folder), oldest first, with each time in this computer's time zone, for a spreadsheet or for keeping; from 1.18.1 the pictures and videos hidden are rows among the tries, each with why in the result column and its address, the nudity and suggestive scores and its mark (hidden by mistake or rightly hidden) in columns of their own, which a try's row leaves empty; from 1.22.0 the Firefox lock's record is rows among them too, Firefox lock in the site column and what the add-on found in the result column, as on Every try; from 1.27.0 the pictures that waited for a verdict are rows too, with their row's words in the result column and the address in its own.

If a listed site's page loaded anyway, because its rules were off, say (or, until 1.21.1, because Firefox had given the extension no access to websites yet), the note says Opened, not blocked and the summary line counts those pages. That means something on the settings page still needs switching on.

The record starts when the extension starts watching, but the browser's own history goes back further: every page loaded in that browser profile, for months in Firefox and 90 days in Chrome, except in private windows and whatever someone deleted. From version 1.3.4, when the extension is installed or updated it looks through that history for visits to listed sites and adds them, with their original times, marked Visited before the add-on (Visited (browser history) until 1.21.0); from 1.11.0 it also looks each time the browser starts, and whenever it finds it hasn't been running for a while (see Was it ever off?). A line on the record page says when it last looked and what it found, and a button there looks again (after adding a site to your list, say). Those entries say the site was visited; whether something else blocked it at the time isn't known. The same visit is never added twice, and a try the extension saw as it happened isn't added again from the history. This is what makes the record an answer to "has this browser been used for such sites", not only from the day the extension arrived.

The browser fills in addresses from its own history and bookmarks, blocked sites included: a blocked try still puts the typed address into the history, where typing its first letter brings it back. So once a try is in the record, the extension takes the site's pages out of the browser's history, and removes bookmarks to listed sites: the earlier visits the history scan found (the record page's line says how many pages and bookmarks went), and each new try a moment after it is noted. The record keeps them all, with their times, so the record page is the place to look, not the browser's own history window. A sweep after a try finds every page of that site, so from 1.11.0 any earlier visits it finds that no look through the history has recorded yet (from a time the extension was off, say) go into the record first: nothing leaves the browser's history without entering the record. Sites pinned by hand on Firefox's new-tab page, and what Firefox suggests from the web rather than from this profile, aren't touched.

No list is complete: new sites appear every week, and the community list lags behind on the newest kind. So the same look through the history also notes sites that aren't on either list but look adult from their names (porn, hentai, nsfw, escort, a .xxx address, and so on, judged with care so that essex.gov.uk and peacocktv.com are left alone). The settings page says how many there are, and a page of its own, Not on the list, but might belong there (linked from the settings page and the record page), lists them, most visited first, with the number of visits and the last one. They are not blocked; Add to your list puts one on your list (the same list as the box on the settings page, which updates), blocks it from then on in that browser, and has the history looked through again, so its earlier visits join the record and it leaves the table. Only the name is judged: a plain name such as swappz.com passes unnoticed, which is why those still need adding by hand when you meet one.

Nothing on either page clears the record, and the pages have no PIN, so anyone who opens them can read it. The record stays until the extension is removed (which the Firefox lock prevents) or the browser profile is deleted, and only the oldest notes go once there are more than 10,000 (1,000 before version 1.3.5). Like the sites you add, it is kept in the browser's own storage for the extension, so Firefox drops it when it quits if the add-on isn't signed, and it never leaves the computer: the add-on still collects no data in Mozilla's sense.

What it doesn't see:

  • Images, scripts and frames that another page loads from a listed site. Those are blocked silently, and they aren't the person's doing.
  • Anything in another browser, or in Firefox's Troubleshoot Mode, where the add-on doesn't run. Firefox's own copy of the list still blocks the built-in sites there, but nothing is noted.
  • Private windows, unless the extension is allowed there (the settings page says whether it is). Under the Firefox lock there are none.
  • Tries while the extension was off, or sites that aren't on either list, unless the browser's history has them (see above, and Was it ever off? below).

To note attempts, the extension asks the browser to tell it about page loads (the webNavigation and webRequest permissions), to read and change its history (history), and to remove bookmarks (bookmarks). Firefox's add-on permission prompt calls those "Access browser activity during navigation", "Access browsing history" and "Read and modify bookmarks". To keep track of when it is running it asks for alarms, which has no prompt.

Was it ever off?

"Has Family Site Blocker ever been switched off?" is the question the record couldn't answer before 1.11.0 (#69): while the add-on is off, in Firefox's Troubleshoot Mode, or removed, it notes nothing, Firefox keeps no history of an add-on being switched off and on, and macOS notes a profile's installation and removal only in logs that are hard to read and don't keep long. So from 1.11.0 the extension keeps its own account, in its storage: when it first started watching in this browser profile, and the stretches of time its background script is known to have been running. It notes the time when it starts, on every page load it sees, and once a minute from an alarm (the alarms permission, which prompts in neither browser). A silence longer than two and a half minutes ends a stretch. The browser's own history then tells the silences apart: a closed browser or a sleeping computer leaves a silence with nothing in it, which is closed up; pages visited inside a silence mean the browser was in use while the extension wasn't running, and that silence is kept as a time it was off, with how many pages the history held from it (the extension's own pages don't count). When a silence ends, the history is looked through for the visits to listed sites made meanwhile.

The record page says what it knows under Was it ever off?: since when the extension has been watching (for a profile that had an earlier version, the earliest try that version noted as it happened, marked "at least", and since when it has kept track), then how often it was off, with the latest time and the pages visited meanwhile, and how many visits to listed sites the record holds from those times, with the latest, or that no such time was found, with a link to Every try, where each time it was off is laid in as a band in its day among the tries, with the visits to listed sites from then under it (a time that crosses midnight shows in each day it touches), and the link shows those times alone. Each visit found in the history is placed the same way, on the record page, in See every try and in the saved file: Visited before the add-on for one from before the extension was installed; Visited while off for one from a silence with the browser in use; Visited before it was listed for one from a time the extension was running, when a listed site's page load would have been noted as it happened, so the site can't have been on a list yet (the list has caught up since); and Visited after the install for one from after the install but before 1.11.0 kept track, when either may be true (until 1.21.0 the four read Visited (browser history), Visited while the add-on was off, Visited before the site was listed and Visited after the add-on was installed). The by-site table counts the visits from times the extension was off under each site, and the settings page's summary counts them too.

From 1.22.0 the record also says when the Firefox lock (see Lock it, so nobody can switch it off), which takes the switch away, was in force and when not, where the settings page's board says so only as of now. Firefox reads the lock's settings when it starts, so the lock can come or go only across a Firefox restart; the add-on's background script, which starts with Firefox, asks Firefox at each of its own starts whether a policy installed the add-on and keeps it from being switched off (the same answer the board's lock line rests on), and when the answer differs from the last time it notes it, with the time of that start, in a record of its own (lockChanges, the latest 1,000). On Every try each note is a row, Firefox lock in the site column and In force or Not in force in the result column, laid in by its time among the tries, with a line that explains the rows and shows them alone (tries.html#lock, where the summary says since when the lock has been in force, or not); the saved file has the same rows. The first check of all says In force when first checked or Not in force when first checked: it says what the add-on found when it began keeping track, with the install or the update to 1.22.0, not since when, so a lock that went before then has no row of its own, and one that goes later gets a row at the Firefox start that found it gone.

What it can't tell: a silence shorter than two and a half minutes (the extension switched off and on again within that time), browsing in private windows or with history switched off, which leaves no visits in the history, and anything done in another browser. The settings page's board says whether the lock, which takes the switch away, is in force, Every try since when (from 1.22.0, above), and a visit's placing is only as good as the computer's clock. The account of running is kept in the extension's storage like the record, so it goes with the profile and never leaves the computer.

Locked-away password

The extension can keep a password that you only get back after a wait you choose, from 1 minute to 2 days. It's meant for putting something out of your own quick reach, such as this computer's administrator password, in the same way as Lockbox Local. It has a page of its own: the settings page's Locked-away password section says where it stands (none, locked away, or how far unlocking has got) and Open the locked-away password page opens it.

  1. On that page, type the password, choose the wait and click Lock it away.
  2. Click Save a backup file. Removing the extension deletes the password with it, and so does Firefox when it quits if the add-on isn't signed. The backup file stays locked with the same wait, so it's safe to keep anywhere; if the wait is lengthened later, save a new one and delete the old, since the file keeps the old wait wherever the extension can't remember the new one (see Changing the wait).
  3. To get the password back, click Start unlocking and leave the page open. When the wait is over the password appears, and it's locked away again straight away with the same wait. To lock it away again with a different wait instead, choose one under the password and click Lock it away again. Copy puts the password on the clipboard, and from version 1.12.2 Lock it away again and Hide clear it from there, so that it isn't left to paste; Lock it away does the same when the password was copied out of its box with ⌘C or Ctrl+C. Closing the page can't: a browser only lets a page write to the clipboard right after a click on it, and the page clears it only when it put it there, since checking what the clipboard holds would need a permission of its own.

Changing the wait. From version 1.10.0 the wait can be made longer at any time, without unlocking: while the password is locked away, choose a longer wait under Lengthen the wait to and click Lengthen the wait. The password isn't needed for that. The locked box, as stored, is locked inside a second puzzle that takes the difference, so getting the password back means solving the outer puzzle, which gives the inner box, and then that one; the page and the settings page's line give the whole wait, and say when it was lengthened. Unlocking goes through the layers in turn, pausing and carrying on as before (Stop unlocking throws away the work on every layer), and locks the password away again as one puzzle with the whole wait. Making the wait shorter needs the password, so that can only be done once it has been unlocked, with Lock it away again (step 3).

Backup files from before. Whichever way the wait grows, a backup file saved before it did can't be changed: it holds everything its own wait takes, and nothing done afterwards reaches into it, so on another computer with the extension it still opens after the old wait. From version 1.13.0 this browser profile doesn't take that path. The extension notes the boxes that have held each password here (each has a 2048-bit number of its own, which can't be changed without breaking its puzzle) and the wait last set for it, and when a backup file of an earlier box is restored, it puts the box inside a longer puzzle that takes the difference, as Lengthen the wait does, before storing it. So "lock it away, save a backup file, lengthen the wait to 10 minutes, delete it, restore the backup file, start unlocking" waits 10 minutes here, and the page and the record say what was done (Restored from a backup file … with the wait lengthened). A backup file of the box stored last restores as it is; a new password locked away gets a wait of its own; the wait follows what is chosen for the password, lengthened, or shorter once it has been unlocked and locked away again; and the last 200 boxes are remembered. Those notes live in the browser profile with the password (see Limits), and the file knows nothing of them, so another profile or computer, or this one once the extension's storage is gone, restores the file with its old wait. So the advice stands: delete those files (and empty the Trash) and save a new one, or make up a new password and lock that away instead. The page says so each time.

The wait is computing time, not a timer. The password is encrypted with a key that can only be worked out by squaring a 2048-bit number over and over, each step needing the one before (a time-lock puzzle), and the number of steps is set by timing this computer. Reading the extension's storage or the backup file, or changing the computer's clock, doesn't skip it. While it runs, one processor core is busy. If the page is closed or the computer sleeps, the work pauses, and it carries on from where it got to when you open the page and click Carry on unlocking. Stop unlocking throws the work away. From 1.13.2 the page asks why before unlocking starts: a reason has to be given, and it goes into the record with Unlocking started and again with The password was shown. From 1.28.0 the reason is chosen from a menu (installing or updating software, changing a system setting, setting up a printer or another device, fixing something that stopped working, trying it out), or typed under Something else; until then it was typed. Carrying on paused work isn't asked again, and the page doesn't judge the answer: it is there to be read later.

From version 1.9.0 the page keeps a record of what has happened, with the time: locked away (and the wait), the wait lengthened (from what to what), unlocking started (and, from 1.13.2, why), paused (from 1.29.0, at how far: the page can't be sure of writing anything as it closes, so the pause is written when the work is carried on or stopped, dated when the progress was last saved, within five seconds of the pause), carried on (and from how far) or stopped (and at how far), the password shown (and when that unlocking started, and why), locked away again (with the same wait, or the one chosen in its place), a backup file restored (and when it was sealed, and from 1.13.0 whether its wait was lengthened to the one set here as it came in), the password deleted. So "was the password unlocked yesterday?" has an answer: look for The password was shown on that day. The record stays when the password is deleted or replaced, and nothing on the page can clear it. Only the oldest entries go once there are more than 500: an unlock is three entries (started, shown, locked away again), one more each time it is stopped and two each time it is paused and carried on, so the record reaches back a hundred unlocks or more. From 1.14.0 the page sums the record up in a line under What has happened (how many entries since when, and the latest), and the entries themselves are rows on Every try, among the tries at listed sites and the times the extension was off, marked Locked-away password, so that what was done with the password can be read beside what happened in the browser (an unlock a few minutes before the extension went off, say); See them among every try shows them alone. From 1.11.4 the record says when it began (its first entry: the first thing done on the page once 1.9.0 had arrived), as the last of those rows, The record began; once the oldest entries have gone, that row says so, and how far back the record still reaches. The settings page's line reads it too: "A password is locked away (since Oct 11, 2026), unlocked once, last on Oct 24, 2026", or "never unlocked", and while unlocking is under way, the day it started; with no password, whether the last one was deleted and when. Only what was done on this page is recorded: not what anyone did with the password afterwards, nor an unlock done on another computer from the backup file, which doesn't carry the record. The record is kept in the browser profile like the record of blocked attempts (see Limits), and it is no harder to tamper with.

What it can't do:

  • Someone who writes a faster program for the same puzzle can shorten the wait, perhaps several times over, though not skip it.
  • It doesn't stop anyone resetting the administrator password another way, such as from macOS Recovery, unless FileVault is on and its recovery key is locked away too (see Make the lock hold against the administrator password, too).
  • A faster or slower computer than the one that locked it takes less or more time.
  • Lengthening the wait can't reach a backup file saved before: that file still opens after the old wait anywhere but this browser profile (which, from 1.13.0, lengthens it as it is restored), so the longer wait only holds everywhere once such files are gone, or the password has been changed.

Limits

  • It is a browser extension. Safari, other browser profiles and apps are not covered; on a phone, only Firefox for Android runs it, without a lock (see On an Android phone). In Firefox it stays installed only until Firefox quits, unless Mozilla signs it.
  • It updates itself only in Firefox, from version 1.3.2, and only while the update files are published (see Let it update itself). In Chrome, Edge and Brave, an extension loaded unpacked is updated by replacing the folder's files and reloading it on the extensions page.
  • Without a lock, anyone who can open the extensions page can turn it off or remove it, and the settings page has no PIN (its Is it working? board says whether the lock is in force). Firefox on a Mac has the lock above, which anyone who knows an administrator's password can take off. In Chrome and Edge, an administrator can force-install the extension with the ExtensionInstallForcelist policy and turn off Incognito with IncognitoModeAvailability, which needs the extension packaged and published. The lock only covers Firefox, so on a child's account, keep other browsers out with account or system controls.
  • The browser's own developer tools sit above the add-on, which runs in the page: the Inspector previews a hidden picture from its address, the Network panel shows the bytes of anything the page loaded, and the Console can read a hidden picture's address or un-hide the page (see Pictures). The Firefox lock turns the developer tools off (from version 1.10.3, by locking the devtools.policy.disabled preference); in Chrome and Edge the same deployment that force-installs the extension can set DeveloperToolsAvailability to 2 (disallowed). Without a lock, anyone who can open the developer tools can reach blocked content through them.
  • Sites added on the settings page are kept in the Firefox profile, so deleting the profile folder loses them (the add-on comes back by itself under the lock). For sites that must stay blocked whatever happens, add them to the built-in list. The records of blocked attempts and of the locked-away password are kept there too, and go with it.
  • The lock installs the add-on once in each Firefox profile. If someone deletes the add-on's file from inside their Firefox profile folder while Firefox is closed, Firefox doesn't put it back: it's missing from the Add-ons Manager until you install it again from the folder.
  • Firefox takes each of its settings from one place. The lock leaves out the one other blockers use for their own add-ons (ExtensionSettings), so theirs keep working, and its other settings are the same as Plucky's, apart from WebsiteFilter (Firefox's own copy of the built-in list). If another program sets Preferences differently, Firefox uses the lock's (which keeps add-ons' blocking switched on) instead of that program's. If another program also sets WebsiteFilter, Firefox uses the lock's list and drops that program's. The same goes for 3rdparty, which carries the lock's stamp: a program that uses it to configure its own add-ons would lose those settings (Plucky doesn't use it). To check before installing the lock on a Mac with another blocker, look for WebsiteFilter and 3rdparty on about:policies.
  • Firefox's own copy of the built-in list takes at most 1,000 entries (five whole adult domains, the large sites and the sites people visit most; see Adding sites), stops pages and frames but not images, scripts or other things an allowed page loads, and shows Firefox's Blocked Page rather than the add-on's. While the add-on runs, it covers the rest.
  • Reaching a site by its IP address, through a proxy or VPN, or through a translation or cache service is not covered unless that address is on the list too.
  • The picture filter judges <img> pictures and <video> frames, by a machine that errs both ways; see Pictures for what it leaves out (backgrounds, protected video, frames the page may not read, the device's own camera).
  • Safe search covers five search engines, with the filters those engines provide; YouTube's Restricted Mode is no longer kept on (it was until 1.25.0, and hid ordinary videos). Reddit, X, Discord, Telegram and other platforms carry adult content under their own domains, which a list can't separate from the rest.

scripts/package-signed.mjs npm run package:signed: puts the signed .xpi from Mozilla in a zip that gives it a clear name and the gate icon in Finder.
assets/finder-icon.icns The gate icon for Finder. npm run icons makes it along with the extension's icons.
test/ Fast checks (*.test.mjs, with the time-lock puzzle in timelock.test.mjs) and the real-browser tests (browser.e2e.mjs for Chromium, firefox.e2e.mjs for Firefox, firefox-lock.e2e.mjs for the Firefox lock, mac-installer.e2e.mjs for the installer package).
extension/mac/family-site-blocker-firefox.mobileconfig The add-on's own copy of the Firefox lock's profile, the same bytes as mac/'s, written by the same build, which the settings page's lock line saves on a Mac when it asks for the profile to be installed (Save the lock's profile, from 1.23.0). Don't edit by hand.
mac/family-site-blocker-firefox.mobileconfig The Firefox lock for a Mac, as a configuration profile: it installs the newest signed version from the update site, carries Firefox's own copy of the built-in list, and hands the add-on a stamp saying which copy it is (the 3rdparty policy, read as browser.storage.managed; extension/lib/lock.js turns it into the settings page's lock line). npm run build (or npm run firefox-lock on its own) makes it from scripts/firefox-lock.mjs and blocklists/.
mac/local.parental-controls.family-site-blocker.firefox-troubleshoot-key.plist The launch agent that closes the Option key (see Close the Option key, too), written by the same script.
scripts/mac-installer.mjs npm run mac-installer, on a Mac: builds the installer package that puts that launch agent in place (dist/mac/), with a postinstall script that closes the key at once for the accounts logged in. Mac files for a release (.github/workflows/mac-installer.yml, by hand) builds it on a GitHub-hosted Mac and adds it to a version's release.
.github/workflows/pipeline.yml Tests and release, on GitHub's Linux machines. On every push to a branch: checks (the fast checks, the Firefox zip and Mozilla's add-on linter) and browsers (the Chromium and Firefox suites, left out when the branch changes nothing they load or run). When a version lands on main: sign (gets the version published on addons.mozilla.org and signed, and publishes the release with its files) and update-files (builds updates.json and the newest signed .xpi files from the releases, and the guide, and pushes them to the project's public site, which the Firefox lock installs from). By hand, from the Actions tab: every suite, or sign and publish alone.
scripts/ci-plan.mjs The plan job of Tests and release: decides which of its jobs a run needs, so the browser suites run only when something they load or run changed, files that passed on their pull request aren't tested a second time on main, and sign and update-files run when the version changes.
.github/workflows/lock-check.yml, mozilla-backup.yml, android.yml, macos.yml, mac-installer.yml Started by hand from the Actions tab: the Firefox lock check (tests the lock with the latest signed release on Linux, on its own, next to another blocker's settings, and arriving after older copies; it fetches version 1.1.1 from Mozilla with the API key that sign uses), the Mozilla backup (saves every version Mozilla has signed in the releases), the Android app (builds the APK and the Play bundle from android/), Tests on macOS (every suite on a GitHub-hosted Mac, and the installer package's own test) and Mac files for a release (above).
test/real-pictures.check.mjs, test/real-pictures.txt, .github/workflows/pictures-check.yml Real pictures check (npm run check:pictures): judges the real pictures listed through the extension in Chromium and prints their scores against what the list expects. Contacts real websites, so it isn't part of npm test. Started by hand from the Actions tab.
scripts/updates-manifest.mjs Makes the update manifest Firefox reads, with each signed version's address and hash, and the rest of the update files.
scripts/check-signed.mjs Checks that a signed .xpi holds exactly the files that were uploaded, plus Mozilla's signature.
scripts/amo-signed.mjs Downloads a version Mozilla has already signed, for the sign job, waiting only as long as it is told for one Mozilla still holds. Tested against a stand-in for Mozilla's API (test/amo.test.mjs).
scripts/amo-backup.mjs Mozilla backup (by hand): saves every version Mozilla has signed in the releases, next to the files sign puts there, so the project keeps its own copies; a version with no release gets one, on the commit that made it (scripts/version-commit.mjs; test/amo-backup.test.mjs).
scripts/guide.mjs Renders this guide as the front page of the project's public site, each heading under the anchor the settings pages link to, with the add-on's icon in the heading and the browser's tab, and puts the lock's profile beside it, for update-files.
scripts/release-files.mjs Fetches the signed .xpi files of the newest versions from the releases on GitHub, for update-files and the Firefox lock check, and puts a file in a version's release, for the Mozilla backup.
scripts/release-notes.mjs What the page of a version's release says, for sign: how to install the version, and what each of its files is.
scripts/ci-summary.mjs Sums up a suite's TAP output in a job's log and fails the job when a test failed or was skipped.
scripts/amo-metadata.mjs The add-on's page on addons.mozilla.org, in words: the summary, the description, the category, the license, each version's release notes and the notes only Mozilla's reviewers see, which sign sends with each version (test/amo-metadata.test.mjs). Nothing in it names anyone.
